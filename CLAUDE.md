# Portfolio

`Iman_Kasim_Portfolio.html` is the main single-file site (inline CSS/JS, Google Fonts) — kept as plain static HTML on purpose, not converted to React. `KASIM_ImanHuson_BSCS-3B_cpu_scheduling.py` is a standalone coursework script, not part of the site. `book-site-react/` and `red-rising-archive/` are two separate, deliberately-kept-both Red Rising Saga fan builds (unofficial fan tribute — not academic work, not linked from the main portfolio's project list) — the first a template worked example, the second a much deeper cinematic archive built after being asked directly whether it should replace the first or stand alongside it (it stands alongside). Both need a bundler, each has its own section below. There was originally also a plain-static version at `book-site/`; it was removed once `book-site-react/` replaced it as that pair's one canonical version, so don't recreate it without being asked. `index.html` at repo root is a landing page linking all sites, needed because GitHub Pages' root URL 404s without one. `docs/website-build-template.md` is the reusable 4-step prompt template these were built from.

## Default approach when asked to build a new site here (read this first)

Every tool listed in this file — skills and libraries both — is available. The point of this section is to make sure they're all *considered*, not that they're all *used*. Stacking every library onto one site is not what makes it look premium; the `web_cheatcodes.pdf` someone sent for this repo ends with the line that actually matters: *"Good design + typography + spacing + 2–3 intentional animations > 50 random effects."* Take that literally.

1. **Direction before tools.** Start with `design-taste-frontend` (plus `brandkit` or `ui-ux-pro-max` if there's no direction yet) to get an actual point of view for *this* project — audience, tone, what "premium" means here — before reaching for any library. A restrained static page with 2–3 intentional touches beats one carrying every tool in this file.
2. **Plain HTML/CSS/JS is the default.** Only add a bundler (Vite + React, per `book-site-react/`) when a specific chosen effect genuinely needs one (`react-bits`, `@react-three/fiber`, Framer Motion). Converting a project to React is a real architecture decision, not a tooling add — ask first, the way `book-site-react/` only happened after being asked directly.
3. **Match the tool to the project, don't stack them all in:**
   - *Landing/marketing page* → direction skill, maybe `Lenis` + GSAP `ScrollTrigger` for scroll feel, then `web-design-guidelines` + `playwright-cli` to verify. No 3D unless there's an actual 3D subject.
   - *Portfolio / resume / academic work* → restraint over spectacle: clean typography, fast load, accessible. This is `emil-apple-design`'s "feedback, spatial consistency, restraint" and the PDF's "don't animate everything," applied hardest — a recruiter or professor isn't the audience for a WebGL showcase (this is why `Iman_Kasim_Portfolio.html` stayed plain HTML).
   - *Deliberately cinematic/showcase project* (like `book-site-react/`) → the fuller stack is fair game, but still pick 2–3 signature moments, not every effect in the PDF's "Premium Website Effects" list. This repo's example used exactly three: one hero starfield, one headline reveal, one metallic-text accent.
   - *3D* (Three.js / React Three Fiber / Drei / Spline, or **`ogl`**) is only for a project with an actual 3D subject — a product, a model, a spatial concept. Bolting 3D onto a page with nothing 3D to show is the "don't load huge libraries for tiny effects" anti-pattern the PDF itself names. Which library: see the hard-won note in the `red-rising-archive` section below — `@react-three/fiber`/three.js did not render reliably in this container even when every internal check (render calls, triangle counts, WebGL context) said it should have; `ogl` (already a dependency via `book-site-react`'s `Particles`) did, immediately and consistently, at roughly a third of the bundle weight. Default to `ogl` for new 3D work here unless there's a specific reason to need three.js's ecosystem (e.g. a specific drei helper with no ogl equivalent).
4. **Verify before calling it premium.** `web-design-guidelines` audit + `playwright-cli` screenshots at 320/375/1440px + an actual no-JS and reduced-motion check — not a skipped afterthought. Two real bugs this repo has already hit were caught exactly this way: a no-JS nav bug in the original static book-site build, and `book-site-react/`'s opacity-gated content going invisible under a full-page screenshot. Something that breaks under a screenshot tool or with JS off isn't premium, it's fragile.
5. **Say plainly whether you're replacing something or adding something new.** When a build like `book-site-react/` starts as a variant of an existing page, say explicitly whether the old version stays live alongside it or gets replaced — "I converted X" is ambiguous between those two and caused real confusion here (see git history around the `book-site/` removal). Default to asking which is wanted before assuming either.

Full tool inventory — what each one is for, and its real caveats — is below.

## book-site-react (React + Vite build)

Source lives in `book-site-react/`; `node_modules/` and `dist/` are gitignored — **the build output is not committed**. It's built and deployed by `.github/workflows/pages.yml`, which also assembles the plain files (root `index.html`, `Iman_Kasim_Portfolio.html`) and `red-rising-archive/`'s build into the same Pages artifact. This replaced an earlier plain-static version at `book-site/`, which was removed once this one superseded it; don't recreate `book-site/` unless asked. Deployment is on **GitHub Actions** (Settings → Pages → Source), already switched — GitHub Pages allows only one deployment source per repo, so this superseded the old "Deploy from a branch" method entirely, for the whole site, not just this project.

Libraries used and why: **Lenis** (smooth scroll) + **GSAP `ScrollTrigger`** (scroll-based reveal), wired via the standard `lenis.on('scroll', ScrollTrigger.update)` + `gsap.ticker` integration in `src/main.jsx`. Three **react-bits** components are vendored into `src/components/` (not npm-installed — that's how react-bits ships): `Particles` (WebGL starfield, `ogl` dependency), `SplitText` (GSAP-driven headline reveal), `ShinyText` (`motion` dependency, metallic sheen on the byline). License is MIT + Commons Clause (`src/components/REACT-BITS-LICENSE.md`) — fine to use in this site, not fine to resell/redistribute the components themselves.

One real trade-off from switching to client-rendered React, not swept under the rug: there's no server-side rendering, so with JavaScript disabled the page shows only a plain `<noscript>` message asking the visitor to enable JavaScript — the original static build (now removed) stayed fully readable with JS off; this one doesn't. That regression was accepted knowingly when the static version was retired in favor of this one, not an oversight.

One bug found and fixed during QA, worth knowing if this pattern gets reused: the scroll-reveal (`src/components/Reveal.jsx`) originally hid content at `opacity: 0` until a real scroll event fired it — which meant a full-page screenshot tool (including `playwright-cli --full-page`, used for this repo's own QA), print/PDF export, or any partial JS failure left everything below the hero permanently invisible. Fixed by never touching opacity: only the lift `transform` animates, so content defaults to fully visible and readable even if the scroll trigger never fires.

Environment note: this container's Chromium needs `--no-sandbox` to launch as root — already set in `.playwright/cli.config.json`'s `launchOptions.args`; don't remove it.

## red-rising-archive (React + Vite + OGL build)

A much deeper Red Rising fan build than `book-site-react/` — full character dossiers, lore/world encyclopedia, a filterable quote vault, a spoiler-level system, and a scroll-scrubbed 3D book carousel — built from a 40-section brief. Deliberately kept as a **separate** project from `book-site-react/`, not a replacement, per an explicit yes/no asked before building it (see point 5 above) — don't merge or remove either without asking again. Same deployment mechanism as `book-site-react/`: source in `red-rising-archive/`, `node_modules/`/`dist/` gitignored, built and assembled by the same `.github/workflows/pages.yml`.

**Fact-checking discipline** (the brief itself demanded this): before writing any character/lore/quote content, real claims were checked against actual sources (Red Rising Wiki, search) rather than trusted from the brief or from memory — house mottos and sigils (Augustus/lion, Bellona/eagle, Telemanus/fox), Pax au Augustus's parentage, character epithets (Diomedes/Storm Knight, Atlas/Fear Knight, Apollonius/Minotaur of Mars), and the actual wording/speaker of quotes (Eo, not Darrow, says "Then you must live for more" — the brief's own "Words That Stay" list had this misattributed). Where a claim couldn't be verified with confidence (some of the brief's "Howler's Creed" phrases, some X/social handles), it's labeled as fan-composed/unverified in `src/data/*.js` and the UI rather than asserted as canon — see `design.md` and the data files' own comments for exactly what's verified vs. not. Extend this discipline to any new content added here, not just the initial build.

**The one real engineering lesson worth carrying forward, because it cost significant effort to find**: the 3D book carousel was first built with `@react-three/fiber` + `three.js` + `@react-three/drei`. It failed to render *at all* in this container — a solid black canvas — despite every internal check passing (correct WebGL context, correct render-call/triangle counts via `renderer.info`, correct camera/geometry math, zero console errors). Chased through several false leads (alpha compositing, tone mapping, `powerPreference`, GSAP's `pin: true` DOM-mutation racing with React Three Fiber's `ResizeObserver`-based canvas sizing — switching to CSS `position: sticky` fixed a real, separate layout bug along the way but not the blank-canvas issue). The fix was replacing three.js/R3F entirely with **`ogl`** (already proven working in this exact container via `book-site-react`'s `Particles` component) — it rendered correctly on the very first try, with no scroll-dependent flakiness, and cut the bundle from 413KB to 145KB gzip in the process. If a future 3D need shows the same "renders internally correct, shows nothing on screen" symptom in this container, don't keep debugging three.js — switch to `ogl` first and confirm, before spending more time on the heavier library.

**Lessons from the first round of user feedback after shipping** (background was flat, scroll felt jittery, books section wasn't usable) — also the round where `design-taste-frontend` should have been run *during* the build and wasn't; it was only actually invoked after the user caught the gap directly. Don't repeat that: run the direction skill before implementation, not as a post-hoc audit.
- **Flat background**: a solid `--charcoal`/`--void` background reads as boring regardless of how good the typography is. Fixed with a fixed, `z-index:0`, `aria-hidden` `.ambient` layer of several low-opacity (8-16%) `radial-gradient`s in the existing red/gold palette, plus a `.vignette` inset box-shadow, sitting behind all content; `section.alt` backgrounds were changed from a solid color to a semi-transparent gradient so the ambient glow actually bleeds through instead of being fully occluded.
- **Scroll jitter root cause was not the 3D rendering** — it was calling `setState` on every `ScrollTrigger` `onUpdate` tick (which fires every animation frame while scrubbing), re-rendering the caption and nav buttons dozens of times a second. `design-taste-frontend` Section 5.D calls this out explicitly (don't track continuous scroll values in `useState`). Fix: keep the raw progress in a `useRef` for the render loop, and only call `setState` when the *rounded* index actually changes. Also pause the OGL rAF loop via `IntersectionObserver` when the canvas host isn't visible, since it's sticky-pinned and only on-screen for part of a long scroll host.
- **Fixed-position elements need their real measured height, not a guessed pixel offset**, when something else needs to anchor above them. `SpoilerBar` is fixed to the viewport bottom and wraps to two lines on narrow viewports, so its height isn't constant; an earlier layout used a hardcoded offset that went negative and clipped the books-carousel scrub dots off-screen with no console error. Fixed by measuring the bar's real `offsetHeight` via `ResizeObserver`, writing it to a `--spoiler-bar-h` CSS custom property, and having anything anchored above it (`.book-caption`) reference that variable in a `calc()`.
- A carousel driven only by scroll scrub with no other affordance is not "user friendly" by itself: added prev/next arrow buttons and clickable/keyboard-navigable (arrow-key) scrub dots that jump via the shared Lenis instance (exposed as `window.__lenis` in `main.jsx`) rather than raw `window.scrollTo`, so programmatic jumps feel the same as manual scroll.
- `emil-review-animations` has `disable-model-invocation` set — it cannot be invoked via the Skill tool by Claude, even to help diagnose a motion complaint. It's reserved for the user to run directly as `/emil-review-animations`. Diagnose motion issues by direct code inspection instead of trying to route around this.

**A `web-design-guidelines` audit run against this project after the round above found four more real, confirmed bugs** — not the same jitter/background complaints, a genuinely separate pass, which is the point of actually running the audit rather than re-inspecting the same three named issues:
- `Reveal.jsx`'s GSAP scroll-reveal tween ran unconditionally. The global CSS `prefers-reduced-motion` rule (`index.css`) only zeroes CSS `transition`/`animation` durations, it does nothing to a JS-driven `gsap.fromTo` tween, so every reveal on the page ignored the OS-level reduced-motion setting. Fixed by checking `window.matchMedia('(prefers-reduced-motion: reduce)').matches` inside the `useGSAP` callback and skipping the tween entirely when true (content is written at its resting position, so it's just immediately visible, not visible-then-jump).
- The exact same fixed-bottom-bar-covers-content bug as the books-carousel fix, just in a different spot: the page footer's `padding-bottom` (40px) was less than `--spoiler-bar-h`, so the fixed `SpoilerBar` permanently covered the footer's last links and copyright line on every page load, not just under scroll. Same fix pattern: `padding-bottom: calc(var(--space-4) + var(--spoiler-bar-h))`.
- The `CharacterDossier` modal (`role="dialog" aria-modal="true"`) never moved focus into itself on open or restored it on close, and didn't lock body scroll — a real, not cosmetic, gap for keyboard/screen-reader users. Fixed with a `tabIndex={-1}` ref that gets focused on mount, `document.body.style.overflow = 'hidden'` while open, and restoring focus to `document.activeElement` from the moment before opening, all in the same `useEffect`/cleanup.
- No `color-scheme: dark` on `:root` (native scrollbar/form-control chrome was defaulting to light, wrong against an all-dark site) and no `<meta name="theme-color">` — both one-line fixes.

Verified all four live via `playwright-cli` (not just "the build succeeded"): screenshots confirmed the ambient background renders and the footer clears the spoiler bar at mobile width; `document.activeElement` was checked via `eval` before/after opening and Escaping the dossier modal to confirm the focus move and restore actually happen, not just that the code looks right.

### Requested but not installed as skills — these are libraries and reference sites, not Claude skills

- **Lenis** (darkroomengineering/lenis), **GSAP** (greensock/GSAP), **Vanta** (tengbao/vanta) — real JS animation/scroll libraries with CDN builds. Could be added to the static HTML via `<script>` tags if a future redesign wants scroll-smoothing or animated backgrounds — not wired in, since that's a real behavior change to the live site, not a tooling install.
- **react-bits** (DavidHDev/react-bits) — real component library; its components are React source files copied in (its own model, not npm-installed), which needs a bundler. Not usable against the plain-HTML main portfolio as-is — this is exactly why `book-site-react/` exists as a separate build. Don't add a bundler to `Iman_Kasim_Portfolio.html` just to reach for this; build (or ask about) a proper React target instead, same as that one was.
- **daisyUI** (daisyui.com) — Tailwind CSS component classes; needs Tailwind (CDN Play mode works for prototyping, not recommended for production).
- **OriginKit** (originkit.dev), **particles.casberry.in** — component/inspiration sites to browse, not installable packages.
- **Three.js / React Three Fiber / Drei / GLSL shaders / Spline** (from `web_cheatcodes.pdf`) — real 3D tooling, same bundler requirement as react-bits, plus real payload weight. Only reach for these when a project has an actual 3D subject to render — see point 3 above.

## Running playwright-cli

```bash
npm install -g @playwright/cli@latest
python3 -m http.server 8765 &          # file:// URLs are blocked by default
playwright-cli open http://localhost:8765/Iman_Kasim_Portfolio.html
playwright-cli screenshot
```

`.playwright/cli.config.json` selects Chromium. In Claude Code on the web, the bundled Playwright expects a newer Chromium than the one pre-installed, so also run `export PLAYWRIGHT_MCP_EXECUTABLE_PATH=/opt/pw-browsers/chromium` (don't run `playwright install`). Locally, run `playwright-cli install-browser chromium` once instead.
